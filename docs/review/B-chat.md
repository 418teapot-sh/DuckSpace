## 🟠 B-01. id 커서 폴링에서 메시지가 영구 유실될 수 있습니다

**위치** `service/ChatService.java:115`

```java
messages = chatMessageRepository.findByRoomIdAndIdGreaterThanOrderByIdAsc(roomId, afterId, pageable);
```

**메커니즘** `chat_message.id` 는 AUTO_INCREMENT 라 **INSERT 시점**에 번호가 정해지지만,
그 행이 남에게 보이는 건 **COMMIT 시점**입니다. 이 둘의 순서는 보장되지 않습니다.

두 참여자가 거의 동시에 보내는 상황을 보겠습니다.

| 시각 | A 의 트랜잭션 | B 의 트랜잭션 | 폴링이 보는 것 |
|---|---|---|---|
| t1 | INSERT → id=10 배정 | | |
| t2 | | INSERT → id=11 배정 | |
| t3 | | **COMMIT** | |
| t4 | | | `after=9` 조회 → **11만** 반환 (10은 아직 미커밋) |
| t5 | **COMMIT** | | 커서는 이미 11 로 전진 |

이후 폴링은 `after=11` 로 들어가므로 **id=10 은 그 클라이언트에서 영원히 안 보입니다.**

**더 나쁜 점** 같은 호출의 131행이 `markRead(room, myId, 11)` 로 읽음 위치까지 11 로
올려버립니다. 그래서 목록 화면의 `hasUnread` 도 false 가 되어 **배지로도 복구되지 않습니다.**
사용자는 메시지가 없어진 줄도 모릅니다.

`before` 스크롤백도 같은 이유로 뒤늦게 커밋된 낮은 id 를 건너뜁니다.

**창의 크기** 두 트랜잭션의 커밋 간격(수 ms)이고, 1:1 채팅에서 양쪽이 동시에 보내야 합니다.
자주 일어나지는 않지만 **한 번 일어나면 복구 경로가 없다**는 게 문제입니다.

**대응 후보**
1. 폴링 시 `after - k` 만큼 겹쳐서 내려주고 클라이언트가 중복 제거 — 서버 변경이 가장 작습니다
2. 커서를 `(createdAt, id)` 복합으로 두고 최근 N초 구간은 매번 재조회
3. 읽음 위치 전진을 "겹침 구간을 제외한 지점" 까지만

시연 규모에서는 1번이 비용 대비 합리적이라고 봅니다. 의견 주세요.

## 🟡 B-02. `size` 를 조용히 깎아서 "지난 대화 끝" 판정을 깨뜨립니다

**위치** `service/ChatService.java:182` (`normalizeSize`) ↔ `controller/ChatController.java:55-56`

컨트롤러 문서가 프론트와 이렇게 계약합니다.

> before 조회로 응답이 **size 보다 짧게** 오면 더 이상 지난 대화가 없다는 뜻입니다.

그런데 서버는 요청 size 를 말없이 바꿉니다.

```java
private int normalizeSize(Integer size) {
    if (size == null || size <= 0) return DEFAULT_PAGE_SIZE;   // 50
    return Math.min(size, MAX_PAGE_SIZE);                       // 100 으로 캡
}
```

**재현** 클라이언트가 `size=200&before=X` 로 요청 → 서버는 100개만 반환 →
클라이언트는 "200보다 짧으니 히스토리 끝" 으로 판단 → **그보다 오래된 대화 전체가
조회 불가능**해집니다. 캡에 정확히 걸릴 때만 발생해서 더 눈에 안 띕니다.

**대응 후보** 응답에 `hasMore` 를 싣거나, 캡을 넘는 요청은 400 으로 거절하거나,
문서의 판정 기준을 "응답이 비면 끝" 으로 바꾸기. 마지막이 제일 싸고 확실합니다.

## 🟡 B-03. 메시지를 보내면 아직 못 본 상대 메시지까지 읽음 처리됩니다

**위치** `service/ChatService.java:145`

```java
ChatMessage saved = chatMessageRepository.save(new ChatMessage(room, myId, content));
markRead(room, myId, saved.getId());   // 내 새 메시지 id 까지 전진
```

읽음 위치는 **전진 전용**이라, 내 메시지 id 로 올리면 그보다 낮은 모든 id 가 읽음이 됩니다.
폴링 간격이 3초라는 게 여기서 문제가 됩니다.

**재현** 상대가 11·12번을 보냄 → 내 다음 폴링(최대 3초 뒤)이 아직 안 돎 →
그 사이 내가 13번 전송 → 읽음 위치가 13 → **11·12 는 화면에 렌더된 적 없이 읽음 처리**.
목록의 `hasUnread` 도 false 라 배지가 안 뜹니다.

주석의 "보낸 사람 입장에서는 이미 읽은 메시지입니다" 는 **내 메시지에 대해서만** 맞는
말인데, 전진 전용 포인터라 남의 메시지까지 딸려 들어갑니다.

**대응 후보** 전송 시에는 읽음 위치를 건드리지 않기 — 내 메시지는 `ChatMessageResponse.of`
가 `isMine` 으로 구분하므로 배지 계산에서 제외할 수 있습니다. 아니면 "내가 마지막으로
실제 조회한 id" 를 넘기기.

## 🟡 B-04. 최초 진입 시 화면에 없던 메시지까지 읽음 처리됩니다

**위치** `service/ChatService.java:131`

커서 없는 최초 진입은 **최신 `size`(기본 50)개**만 반환하는데, 읽음 위치는 그 페이지의
마지막(= 방 전체의 최신) id 로 전진합니다.

**재현** 안 읽은 메시지가 50개를 넘는 방 — 읽음 위치 100, 총 200개 —
에 들어가면 151~200 만 내려가면서 읽음 위치는 200 이 됩니다.
**101~150 은 한 번도 표시되지 않은 채 읽음**이 되고, 위로 스크롤해도 `before` 경로는
읽음을 안 건드리므로 배지로 되돌아오지 않습니다.

B-03 과 같은 계열(읽음 배지가 조용히 사라짐)이라 함께 고치는 게 맞습니다.

## 🟡 B-05. `getMyRooms` 에 페이지네이션이 없습니다

**위치** `service/ChatService.java:66`

```java
List<ChatRoom> rooms = chatRoomRepository.findAllByParticipant(myId);   // 전부
...
chatMessageRepository.findLastMessagesOfRooms(roomIds)                   // IN (방 개수만큼)
...
.sorted(...)                                                            // 애플리케이션 정렬
```

참여한 방을 전부 로드하고, `IN` 절에 방 개수만큼의 파라미터를 넘긴 뒤 메모리에서 정렬합니다.
**N+1 은 없습니다**(마지막 메시지·닉네임 모두 쿼리 1회로 묶여 있음 — 이 부분은 잘 돼 있습니다).

방이 수천 개인 사용자에서 `IN` 절 파싱 비용과 응답 크기가 선형으로 늘고, Hibernate 의
IN 파라미터 패딩과 맞물려 플랜 캐시도 흔들립니다.

**대응** 커서 페이징 도입. 다른 목록 API 와 같은 패턴이라 `Paging` 헬퍼를 그대로 쓰면 됩니다.
다만 **시연 규모에서는 급하지 않습니다** — 우선순위 최하로 두겠습니다.

## 확인했고 문제 없던 것

리뷰에서 중점으로 지정했던 항목들입니다. 다 깨끗했고, 근거를 남겨 다음에 다시 의심하지
않도록 합니다.

**권한 검증** — `getMessages`/`sendMessage` 모두 `getRoomAsParticipant` 로 방 존재(404)와
참여자 여부(403)를 검사합니다. 모든 메시지 쿼리가 `roomId` 로 필터링되므로 **남의 방
커서를 넣어도 교차 유출이 없습니다.** `getMyRooms` 는 JWT 의 userId 만 쓰고,
`/api/chat/**` 는 `SecurityConfig` 의 공개 목록에 없어 기본 인증 필수입니다.

**커서 경계** — `IdGreaterThan`/`IdLessThan` 이 모두 배타적이라 경계 메시지의 중복도
누락도 없습니다. 최초 진입과 스크롤백 모두 DESC 조회 후 reverse 라 오름차순 계약을 지킵니다.
(B-01 은 경계 조건이 아니라 트랜잭션 가시성 문제라 별개입니다)

**방 생성 동시성** — `ChatRoomRegistry` 가 `REQUIRES_NEW` 로 분리돼 있고, 유니크 위반 시
실패 트랜잭션을 통째로 버리고 새 트랜잭션에서 재시도합니다. **재시도가 1회뿐이어도
충분합니다** — InnoDB 에서 패자의 INSERT 는 승자가 커밋할 때까지 블로킹된 뒤에야
duplicate-key 를 받으므로, 예외를 받은 시점에 행은 이미 커밋돼 있습니다.
`ChatRoomConcurrencyTest` 가 8스레드로 실증합니다.

**N+1 없음** — `getMyRooms` 의 마지막 메시지·닉네임이 각각 쿼리 1회입니다.
`message.getRoom().getId()` 도 추가 쿼리를 안 냅니다 — 앞선 조회로 방이 이미 영속성
컨텍스트에 있고, `ChatRoom` 이 필드 접근이라 프록시여도 식별자 getter 가 초기화를
유발하지 않습니다.

**`clearAutomatically = true` 위험 없음** — 리포지토리 javadoc 의 경고대로,
`markRead` 이후 DTO 매핑이 detach 된 엔티티의 기본 필드만 읽고 지연 로딩을 건드리지
않습니다. `sendMessage` 의 `saved.getCreatedAt()` 도 IDENTITY 즉시 INSERT +
`AuditingEntityListener` 의 `@PrePersist` 로 이미 채워진 값이라 안전합니다.

**읽음 위치 역전 방지** — `markReadForUserA/B` 가 `where ... < :messageId` 가드가 걸린
원자적 UPDATE 라 탭 두 개가 동시에 폴링해도 뒤로 밀리지 않습니다. 새 메시지가 없는 폴링은
`!messages.isEmpty()` 가드로 UPDATE 자체를 건너뛰어 3초 폴링의 쓰기 부하도 없습니다.

**정렬** — `Comparator.nullsLast(reverseOrder())` 가 메시지 없는 방을 뒤로, 나머지를
최신순으로 둡니다. 의도대로입니다.

**메시지 길이 검증** — `@Size(max=1000)` 은 Java UTF-16 code unit 기준이라 MySQL
`varchar(1000)`(문자 기준)보다 항상 엄격합니다. 이모지 같은 서로게이트 쌍에서도
오버플로가 나지 않는 방향입니다.
